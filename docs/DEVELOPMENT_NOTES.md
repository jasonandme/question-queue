# 开发决策与迭代记录

这份文档记录功能为什么出现、实现中做过哪些取舍，以及问题、约束和决策之间的关系。

## 1. 从“立即追问”改成“延迟追问”

最初的问题并不是缺少记事工具，而是阅读长回答时很难同时保持两件事：继续理解当前内容，以及记住刚刚产生的疑问。如果立即发送追问，阅读节奏会被打断；如果复制到其他软件，问题与来源又容易分离。

第一版因此只做一个短流程：记录问题、保留可选上下文、稍后填入。数据放在浏览器本地，避免在原型阶段引入账号、服务器和同步冲突。

这一阶段确定了两个后来一直保留的原则：

- 扩展只追加到输入框，不覆盖用户草稿。
- 扩展不自动点击发送，最终内容始终由用户确认。

## 2. “能用”之后先解决可靠性

浏览器扩展更新后，已经打开的网页不会自动重新注入内容脚本。用户看到的现象通常只是点击图标没有反应，原因却可能是扩展未重新加载、网页未刷新，或者当前页面不在支持列表中。

0.1.1 没有急着增加更多功能，而是补充状态检测和清晰的刷新提示。这个改动说明：对于嵌入第三方网站的工具，可诊断性与功能本身同样重要。

## 3. 单条记录无法覆盖真实使用方式

实际阅读中，问题可能一次产生很多，也可能在不同段落中逐渐积累。下一次提问也不一定一次完成。由此出现了三个具体要求：

1. 多次填入不能覆盖前一次填入或用户手写草稿。
2. 需要多选，而不是只能“全部填入”或逐条点击。
3. 浏览器重启后，已经填入但尚未回答的问题应能重新恢复。

0.2.0 将记录状态拆成待输入、已输入、已回答、已掌握。“已输入”不是终点，而是可恢复的中间状态。批量填入会生成带编号的问题列表，但仍然只写入编辑框，不替用户发送。

## 4. 从问题列表走向学习记录

问题积累到一定数量后，单纯按时间排列不利于复习。这里增加了两个出口：

- Word 导出用于长期归档和离线整理。
- 思维导图用于按主题回顾问题之间的关系。

思维导图采用按需调用，而不是后台自动分析。请求范围被限制在问题文本、状态和匿名 ID；上下文、笔记、来源链接及完整回答不发送。这样既降低无意传输私人内容的风险，也让不开启模型功能的用户继续获得完整的本地体验。

API Key 保存在客户端只适合个人使用。面向公众的托管版本应当使用服务端代理、用户级额度和可撤销令牌，不能在扩展中内置共享密钥。

## 5. 覆盖式抽屉与阅读页面发生冲突

网页内抽屉的优点是兼容性高，缺点是它与回答争夺同一层页面空间。打开抽屉时遮挡内容，关闭后又失去随手记录的入口，这与“不打断阅读”的目标相矛盾。

0.3.0 改用浏览器原生 Side Panel。浏览器负责把网页和清单并排布局，清单可以长期打开。网页内抽屉没有完全删除，而是作为旧浏览器的回退方案。

被放弃的替代方案包括：

- 给网页正文强制增加右边距：容易破坏不同网站的响应式布局。
- 使用半透明悬浮窗：仍然遮挡内容，并且键盘焦点管理复杂。
- 只保留弹窗：弹窗失去焦点后会关闭，不适合持续记录。

## 6. 全局列表缺少对话边界

当记录来自多个模型和多个对话时，只显示平台名称不够。同一个平台中的不同主题会混在一起，回顾时看不出问题属于哪段讨论。

0.4.0 将来源拆为两层：平台和具体对话。对话标识优先使用 URL 的 origin 与 pathname，忽略查询参数和 hash；页面标题用于显示。这样可以在标题变化时维持分组，也尽量避免同名对话冲突。

标签被设计为手动信息，而不是强制自动分类。自动标签看似省事，但容易在用户没有检查时引入错误分类。当前实现允许逗号、分号或换行输入，去重后最多保留 20 个标签。

旧数据没有对话字段时，不执行一次性迁移，而是在读取时根据已有来源 URL 和标题推导。这个选择减少了升级失败导致的数据风险，也让 JSON 备份保持向后兼容。

## 7. 从模型回答扩展到知识网页

问题并不只产生在大模型回答中。阅读技术文章和社区问答时，同样需要保留原文、继续阅读，并把疑问留到合适的大模型对话中统一提问。0.5.0 首先适配 CSDN 与知乎，但没有把两组选择器直接散落在页面脚本里，而是建立共享站点适配层。

适配层把网页分成三类：

- `chat`：可以记录，也可以向输入框追加问题。
- `article`：识别正文标题与规范链接，只负责采集和归档。
- `page`：通过工具栏或右键保留基础标题与链接。

知识网页禁止执行批量填入。这是一条安全边界：CSDN、知乎也存在搜索框、评论框和编辑器，复用通用输入框选择器可能把问题写到错误位置。用户切换到支持的大模型对话后，原有多选、追加和状态流程继续生效。

文章来源优先采用页面声明的 canonical URL，并去除常见分享追踪参数。标题优先读取站点正文标题节点，再回退到 Open Graph 或浏览器标签标题。相关规则通过不依赖浏览器的回归测试验证，便于后续增加更多知识网站。

## 8. 当前边界

- 模型网站的输入框和回答节点会改版，选择器需要持续维护。
- 数据默认只在单个浏览器配置中存在，跨设备依赖手动 JSON 备份。
- 自动判断“已回答”依赖页面结构，只能作为辅助状态，用户可以手动修正。
- 刚创建且尚未命名的对话只能显示平台级临时名称。
- 客户端 API Key 方案不适合作为商业版的共享凭证架构。

## 9. 后续改动的判断标准

新功能进入主线前应回答四个问题：

1. 它是否减少了记录和恢复问题的操作成本？
2. 它是否会覆盖、发送或外传用户没有明确确认的内容？
3. 浏览器或模型网站改版后，失败是否容易被发现和解释？
4. 数据格式能否与旧版本兼容，或提供可验证的迁移路径？
